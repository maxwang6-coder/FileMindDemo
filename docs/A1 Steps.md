### 数据库可以类比两张登记表

`roots` 的一行代表一个授权资料目录：

- id：目录别名，例如 demo。
- path：规范化后的本机完整路径，只存在本机数据库。
- dev：操作系统的设备号，后续判断磁盘边界。
- enabled：是否启用。
- cloud_allowed：是否允许云发送，默认否。

`files` 的一行代表一个文件：

- id：应用生成的 UUID，区别于文件名，也不是内容哈希。
- root_id、relpath：属于哪个根、在根内什么位置。
- dev、ino：操作系统设备号与 inode，供后续身份协调。
- size、mtime_ns、ctime_ns：大小与时间；Mac 上 ctime 不能当创建时间。
- sha256：内容指纹，本轮为 NULL，后续计算。
- content_rev、path_rev：内容/路径版本，初始为 1。
- status：本轮为 discovered，表示刚登记，不能当作正文 ready。
- first_seen：首次登记的 UTC 时间。

外键防止文件引用不存在的 root；活跃相对路径唯一约束防止同一位置重复登记。D01 和 D06 两个文件分配不同 UUID，但字节完全相同；此时未计算哈希，不能宣称已验证哈希相同。

manifest 必须对应真实 file_id，因此生成器直接登记自己创建的样例。以后扫描器要按已有路径协调这些记录，不能给所有样例重新发 ID。

### 路径检查做了什么

本机配置加载与根登记都检查根路径及其祖先不含符号链接，DATA_DIR 不在资料根内；数据库根登记还拒绝根之间重叠、已有 root_id 换绑其他目录或设备。

先检查用户原始路径，再规范化，避免先 resolve 后把符号链接痕迹隐藏。目录遍历基础只列目录，不进入符号链接、隐藏目录、应用包、常见系统/云目录和跨设备子目录。它不读取文件内容，也不处理身份或权限失败状态。

这些检查是本地单用户防误操作边界，不保证防御恶意并发修改目录。云目录排除按常见名称与位置工作，不能自动识别任意第三方同步目录；选择根时仍应使用本地非同步目录。

### 命令和服务如何配合

若要让网页服务读取样例授权配置：

```sh
.venv/bin/python -m app.main --config data/config.local.demo.toml
```

此命令只是读取配置，仍不会开始扫描。默认启动不自动读取这份额外配置，也不自动给网页增加修改根目录的接口。

初始化/样例 CLI 与服务共享 DATA_DIR 进程锁。旧服务运行时先正常停止再运行这些 CLI，不删除锁文件。已有数据库在服务启动时校验版本，不支持版本拒绝启动，不自动重置或猜测迁移。

## 第二步 普通文件遍历与元数据清点

依据手册 A1 照做步骤第 2 项，实现“列出允许文件，收集文件系统信息”。当前没有哈希、身份协调或扫描入库，也不修改源文件。第一步见[数据库、样例和目录边界](#step-1)。

### 使用方式

在仓库根目录运行：

```sh
.venv/bin/python -m scripts.scan --config data/config.local.demo.toml --root-id demo
```

配置文件授权本次可以访问的 ROOT_PATH；root_id 选择数据库中的登记记录，二者必须匹配。目录记录必须启用，设备号不能变化。不能仅凭数据库里曾登记过一个目录，就越过当前配置授权读取它。

CLI 使用与服务相同的 DATA_DIR 锁。旧服务持锁时正常停止旧服务，不删除锁文件。命令只输出 JSON，不启动网页或后台扫描，不把结果写成日志文件。

### 输出的字段

| 字段 | 含义 |
| --- | --- |
| root_id | 本次查询的目录编号，如 demo |
| mode | metadata_only，明确不是完整索引 |
| complete | 是否成功完成本次允许范围的清点 |
| file_count | 符合规则的普通文件数量 |
| files | 每个候选文件的元数据记录 |
| skipped | 对已访问目录中条目的跳过原因计数，不是被排除子树内的全部文件数量 |

每条 files 记录：

- relpath：相对于根的路径，例如 `课程/讲义.txt`；不会只保留 basename。
- size：字节数，中文字符数不等于字节数。
- mtime_ns：内容修改时间，整数纳秒时间戳。
- ctime_ns：文件状态变更时间；Mac 上不是文件创建时间。
- st_dev：操作系统设备号。
- st_ino：inode 编号，只有结合设备号与后续规则才有身份意义。

没有 file_id 和 sha256：这是当前文件系统观察，不是已协调身份的文件记录。数据库中样例生成器预分配的 UUID 保持不变。

### 核心过程

1. `get_registered_root` 以只读数据库连接读取 roots，验证本机配置、路径、启用状态和设备号。
2. `iter_scan_directories` 提供允许进入的目录，不跟随链接或进入排除目录。
3. `os.scandir` 列出每个目录的条目，不读取文件正文。
4. `path.lstat()` 检查条目自身，先排除链接，再确认是普通文件。FIFO 等特殊文件不会被打开。
5. 白名单只允许 `.txt`、`.md`、`.pdf`、`.docx`，不区分大小写。格式是否损坏留到解析阶段，不因 `.pdf` 后缀就证明内容有效。
6. 收集元数据并返回 FileMetadata；不同相对路径独立保留，即使同名或同内容。

`FileMetadata` 使用 dataclass，可以类比只有字段的 Java DTO；`frozen=True` 防止普通属性赋值。`MetadataReport` 包装本次输出，列表和字典本身仍是普通可变容器，不宣称深度不可变。

隐藏文件、排除名称/后缀、符号链接、非普通文件和不允许扩展名均跳过。跨设备子目录不进入，跨设备普通文件也不接纳。仍不保证识别任意云同步目录或抵御恶意并发路径替换。

### 本次明确不做

- 不打开正文、不算 SHA256、不提取 PDF/DOCX 文本。
- 不更新 files/roots，不改 manifest，不分配 UUID，不递增版本。
- 不判断改名、复制或删除，不将缺失项标为 missing。
- 不实现页面扫描按钮、后台轮询或新的 API。
- 第二步交付时不支持 `--verify-content`；第三步已增加分块哈希用途，见下文。

超过 MAX_FILES 或遍历/stat 失败时，CLI 输出 complete=false 并非零退出，不返回一个截断后冒充完整的文件列表。权限失败的范围级恢复与 unavailable 持久化属于步骤 5；当前保守地让整次清点失败，旧数据不动。

## 第三步 分块 SHA256 与读取稳定性

2026-11-02 实现手册 A1 照做步骤第 3 项，并沿用前两步的根授权、目录排除与类型白名单。没有身份协调、扫描入库或全文解析。实现位于 [scan.py](../app/scan.py)，终端入口为 [scripts/scan.py](../scripts/scan.py)。

### 怎样运行

```sh
.venv/bin/python -m scripts.scan --config data/config.local.demo.toml --root-id demo --verify-content
```

不带 --verify-content 仍是第二步的 metadata_only，不读源文件字节。带参数时输出 content_hashes，SHA256 只用于内容比较，不代替 UUID。默认每文件 20MiB，来自手册第 5 章规模限制；本机可用 `--max-file-mib 30` 调整，必须是正整数。

### SHA256 可以理解成内容指纹

文件的字节按顺序经过 SHA256，得到 64 个十六进制字符。文件名字不是计算输入；字节相同的副本会得到相同哈希，但仍然是两个文件。指纹不是加密后的原文，也不是文件格式或语义正确性的证明。

`_read_sha256` 创建一个哈希对象，每次 read 请求 1MiB（1,048,576 字节），将块交给同一个 digest.update，最后 hexdigest。不是把多个块的独立哈希拼起来，也不一次把整个文件装入内存。实际总内存还包含 Python 和读取缓冲等，不能宣称整个进程只占 1MiB。

### 怎样检查读取期间有没有变化

1. 先收集第二步的候选元数据，再核对当前根授权。
2. 安全打开源文件，用 fstat 检查实际打开的对象必须是授权设备上的普通文件。
3. 第一次尝试比较枚举快照与打开时状态；如果已经变化，先不读，进入延迟重试。
4. 保存读取前的设备号、inode、大小、mtime_ns、ctime_ns。按块读完整个文件，记录总字节数。
5. 读取后再次 fstat；五项必须相同，总字节数也必须等于读取前大小。
6. 安全重开同一路径但不再读取正文，确认该名字现在仍对应刚才的对象。防止旧文件描述符指向被移走的文件，却把其哈希当成当前位置内容。
7. 首次发现变化，丢弃本次 digest，等待 1 秒后从头重算一次。第二次仍变化，标 unstable，sha256=null。

1 秒是当前实现参数，手册未规定具体间隔。测试传入假的 sleep 回调，只记录等待要求，不让测试真的等 1 秒；测试代码在指定读取节点修改临时文件来制造变化，不靠长时间 sleep 碰运气。

mtime 相同、大小相同也不能直接认为没变，所以同时比较 ctime 和身份信息。它们仍不是绝对保证：文件可以在最后检查之后再次变更，后续索引和查询必须继续校验版本；也不能据此证明没有其他程序持有一个暂时没写入的文件句柄。

### 为什么不用普通 open 直接读取

从列出文件到打开它之间，文件或父目录可能被替换。`_open_hash_source` 使用只读文件描述符、逐层 dir_fd 与 O_NOFOLLOW，拒绝沿相对路径的符号链接打开。最终加 O_NONBLOCK，并在读取前用 fstat 检查普通文件，避免源文件换成 FIFO 后 open 永久阻塞。

这条实现路径面向当前 Mac/Unix；Windows 支持需要另行适配验证。仍不宣称可防御同账号恶意进程持续替换路径，也不是整个文件系统的原子快照。

### 返回状态怎么看

| status | sha256 | 含义 |
| --- | --- | --- |
| stable | 64 位十六进制字符串 | 本次字节读取通过稳定性检查，不等于正文 ready |
| unstable | null | 两次尝试都观察到变化，不能作为当前索引输入 |
| failed | null | 权限、路径、文件消失或 IO 问题，不能作为索引输入 |
| too_large | null | 初始大小超限或读取中增长超限，不计算截断哈希 |

attempts 为实际尝试次数，最大 2；错误或超限不会无限重试。失败项携带的元数据是初始观察，不能当作已验证的当前版本。error_code 给出机器可读原因，不包含正文。

file_count 是候选总数，stable_count 是稳定读完的数量。任何候选不是 stable，则 complete=false，CLI 非零退出；其他稳定结果仍在报告中，但不能把整次操作说成全成功。目录枚举阶段若先失败，则沿用第二步的整次中止行为。

### 数据库与文件是否改变

本步骤只读源字节，不修改名称、内容或权限，不改 roots/files/manifest、不生成或替换 UUID。报告里的状态不是直接更新 files.status；当前尚没有索引写入，unstable/failed/too_large 不产生可用 digest，后续实现只能接纳 stable 输入。

数据库中样例的 sha256 仍保持原来的 NULL，discovered 也不因本轮报告变成 ready。读取可能由操作系统更新访问时间 atime，因此不能笼统说所有文件系统时间都绝对不变。

## 第四步 UUID 文件身份协调与同步入库

2026-11-02 按手册 A1 照做步骤第 4 项及第 23、26 章完成。复用前面三步的授权、遍历、稳定哈希；新增身份计划及显式 SQLite 同步。没有实现第五步的范围级 unavailable、持久扫描记录与 UI，也没有解析、搜索或模型调用。

### 先把三个“编号”分清

把 files 表想成文件登记簿。一行记一份文件，既要知道它“叫什么、在哪”，也要知道“它是不是以前登记的那一份”。

| 字段 | 比喻 | 真正作用 |
| --- | --- | --- |
| id / file_id | FileMind 发的身份证号 | UUID 字符串，数据库列叫 id，报告和 manifest 叫 file_id；不是哈希 |
| relpath | 家庭住址 | 相对于授权根的路径，例如 notes/meeting.txt |
| dev + ino | 文件系统的设备与对象编号 | 辅助识别同盘对象；不能单独证明永久身份，inode 可能复用 |
| sha256 | 内容指纹 | 判断字节是否相同；复制品也有相同指纹，不能代替身份证 |
| content_rev | 内容第几版 | 已知内容改变时加一，初始为 1 |
| path_rev | 地址第几版 | 确认同一文件改名/移动时加一，初始为 1 |
| first_seen | 首次登记时间 | 保留身份时不改，UTC 时间 |

例如 A.txt 复制为 B.txt：两份内容指纹一样，但确实是两份文件，必须发两个不同 UUID。反过来，A.txt 的文字被编辑，虽然指纹变了，它仍可以沿用原编号，只增加内容版本。

### 判断顺序与状态表

必须按顺序判断，不能先看哈希就把相同内容全部合并。

| 情况 | UUID | 版本与状态 |
| --- | --- | --- |
| 同一根、同一有效相对路径，内容没变 | 保留 | 版本不变；时间等元数据变化可以单独更新 |
| 同路径，已有哈希发生变化 | 保留 | content_rev +1，status=stale，提醒后续旧解析不能直接复用 |
| 同路径，旧哈希为 NULL | 保留 | 补初始哈希，报告 initialized，不凭空推测过去是否改过内容 |
| 旧路径已消失；新旧 dev/ino/hash 一致且一对一、当前无硬链接歧义 | 保留 | 更新 relpath，path_rev +1，content_rev 不变 |
| 全新文件、复制品、改名同时改内容、证据不足或硬链接歧义 | 新 UUID | 新行 discovered，两个版本从 1 开始；确认消失的旧行标 missing |
| 已 missing 的历史路径再次出现 | 新 UUID | 不凭同名复活历史身份，旧行保留 |
| 读取不完整或旧路径不能可靠确认 | 本次不应用 | 整批不写，旧记录保持原样 |

“路径优先”也意味着：编辑器通过临时文件替换保存，导致 inode 改变，但路径相同时仍按同路径更新。它不是严格追踪操作系统对象的取证系统。

判断改名时，旧记录必须已有哈希，旧匹配项和本次匹配项都恰好一个；当前 st_nlink 还必须为 1。硬链接可让几个名字指向同一个底层对象，包括根外的另一个名字，因此这里保守地不猜。旧路径消失通过逐层不跟随链接的目录检查确认；大小写变化也按实际目录项拼写判断。

missing 只是“登记簿上记着以前见过，现在确认不在原位置”，不会删除数据库行，更不会删除磁盘文件。尚未开始建全文或向量索引；stale 目前只是为后续解析保留正确状态。

### 代码分工和一次执行的过程

- [identity.py](../app/identity.py) 的 plan_identity_changes：接收旧记录和稳定观察，像拿两份名单对账，生成“新增、更新、改名、缺失”的计划。它不打开资料，也不执行 SQL。
- [scan.py](../app/scan.py) 的 sync_file_identities：负责统筹授权、进程锁、哈希、确认旧路径消失、复核观察及提交计划。
- [db.py](../app/db.py) 的 read_file_records / apply_file_records：读取旧登记簿，校验快照，并把计划写入应用数据库。所有文件值通过 SQL 参数绑定，不拼接成 SQL 代码。
- [scripts/scan.py](../scripts/scan.py)：解析终端参数，输出 JSON 报告，失败返回非零退出码。
- [test_file_identity.py](../tests/integration/test_file_identity.py)：在临时目录制造各种情形，检查规则和数据库结果。

实际流程：

1. 当前本机配置必须授权这个根，并与 roots 中路径、设备号、启用状态一致。
2. 持有同一 DATA_DIR 的进程锁，避免项目服务或另一个同步命令同时占用应用数据。
3. 遍历并稳定分块哈希；任一结果非 stable，本次不应用。
4. 读取旧记录。对未观察到的旧路径安全确认是否消失；若仍存在却不再是可接纳的普通文件，例如被替换为链接，本次不应用，不能谎报 missing。
5. 复核文件状态，生成身份计划；提交前再次复核来源和授权。
6. 开短 SQL 事务，核对 roots 和旧记录快照仍未改变，然后执行整批更新。中途任何 SQL 错误都回滚，不出现“只登记了一半”的结果。
7. 输出每个文件的 action、file_id、两个版本、状态，以及 counts、complete、applied。renamed 还带 old_relpath。

事务像把一整页登记先写在草稿纸上，确认无误才整页入册。长时间读文件不占着 SQLite 写事务；进入事务后只做核验与写库。快照校验还能防止覆盖绕过本项目锁直接修改数据库的操作。

复核不是把整个文件系统冻结起来：最后检查之后仍可能发生外部修改，不能宣称它是原子快照或能抵御同账号恶意进程。后续真正打开/操作文件仍需再次校验。

## 第五步 范围故障隔离、扫描报告与页面

### 最重要的区别：没看到不等于不存在

把授权目录想成一栋楼，每个子目录是一间屋子，数据库是上次盘点的登记簿：

- 屋门打开并完整检查，原来的文件确实没有了：有依据标 missing。
- 屋门打不开：只能说 unavailable，不能说屋里东西全被搬空。
- 一间屋门打不开，其他能正常进入的房间仍继续盘点。

正式扫描为每个完整成功枚举的目录记下这次实际看到的名字。某个目录在枚举中途报错，整份目录名单都不能作为缺失依据；不会拿“看到一半的名单”判断另一半被删除。

| 情况 | 数据库处理 | 其他正常范围 |
| --- | --- | --- |
| 新增、修改、唯一改名、复制 | 继续按第四步身份规则 | 正常更新 |
| 成功完整遍历后确认旧路径消失 | missing，保留历史 | 正常更新 |
| 子目录枚举失败，包括中途失败 | 该范围旧记录 unavailable | 继续更新兄弟范围 |
| 单项 stat 失败、旧路径变成链接或不再可接纳 | 旧记录 unavailable，不当删除 | 继续更新 |
| 单文件读取失败或持续变化 | failed / unstable，隐藏当前内容 | 继续更新 |
| 单文件超限 | 报告 too_large，数据库 unsupported | 继续更新 |
| MAX_FILES 总量超限、提交前来源变化、数据库冲突 | 本批文件更新不应用，记录失败任务 | 不伪造完整成功 |

unavailable 和 missing 都是程序登记状态，不会改变原文件。当前尚无搜索页面；“暂隐藏”体现在旧行被置为非可用状态、正式报告 files 只包含稳定成功项。后续搜索只能取允许的状态和当前版本，不能绕过这些状态直接读旧正文。

恢复访问后再次扫描，同路径继续保留原 UUID。旧行保留最后已知哈希，仅供历史内容比较；它不是当前可用哈希。这样恢复后若内容确实改变，content_rev 仍能增加。失败观察本身的 sha256 为 null，新失败文件也没有可用哈希。

### 报告像每次盘点留下的回执

以前终端报告关闭后不方便查，现在每次正式扫描都有 scan_id，保存开始/结束 UTC 时间、数量、错误码及结构化结果。网页和 CLI 使用同一份报告。相对路径与必要元数据只保存在本机应用数据中，不包含正文、token 或用户绝对路径。

报告主要字段：

- mode=root_scan，scan_id 是这次扫描的编号，不是文件编号。
- counts.scanned 是本次普通候选文件数；stable 是通过稳定读取的数量，failed 是未稳定读取的数量；stat 失败不冒充已成功观察的候选。
- added/initialized/modified/renamed/metadata_updated/unchanged 是稳定文件的身份处理计数。failed/unavailable 另计，不和稳定成功项混在一起。
- missing 是本次新确认缺失数，unavailable 是本次无法观察的旧记录数；已 missing 历史不反复算成新删除。
- skipped 是跳过项的原因分组：隐藏/排除名、符号链接、非普通文件、扩展名、其他设备、不可遍历目录。它统计项，不能都理解为文件数。
- errors 是相对路径与错误码；failed_files 的失败哈希为 null。
- completed_directories 是本次完整成功枚举的范围。它们是缺失判断的证据，不是未来持续有效的磁盘快照。

| complete / applied | 意义 |
| --- | --- |
| true / true | 本次观察与更新完整成功 |
| false / true | 已保存正常范围更新和故障状态，但存在未成功项 |
| false / false | 全局异常，本批文件更改未应用 |

CLI 非完整扫描返回非零退出码，但部分成功不等于数据库全部回滚。全局中止时已知错误会被保存，无法可靠统计的候选总数为 null，不假装是零。成功/部分成功的报告与 files 更新在同一个 SQL 事务，避免“报告说成功，但登记没写上”的正常异常路径。

### 为什么新增 jobs 与 idempotency 两张表

[db.py](../app/db.py) 将 schema 1 显式迁移到 2，仅新增 jobs/idempotency，原 roots/files 及 UUID 不变：

- jobs：任务登记簿。id 同 scan_id，保存 queued/running/succeeded/failed/interrupted、尝试次数、起止时间、错误码与报告 JSON。
- idempotency：请求回执表。同一个请求编号和相同参数再次到达，返回同一个 job_id；同编号换参数返回 409，不悄悄执行另一项任务。

迁移在 init_db、正式扫描 CLI 或服务启动时持进程锁执行；未知版本仍拒绝，不重建或清空旧库。未初始化的 A0 服务仍可启动，但扫描前需登记数据库和本机授权根。

jobs 的 succeeded 表示扫描任务已执行到提交结束，不等于每份资料都成功。部分成功时 error_code=partial_scan，必须结合 result.complete 看。服务异常退出留下的 queued/running 会在下次启动标 interrupted，用户主动重试，不自动重放。

### 网页到后台是怎样接起来的

[schemas.py](../app/schemas.py) 用 Pydantic 定义 ScanRequest，只接受 root_id 与布尔 verify_content，拒绝额外的路径字段。A1 初次与手动扫描始终完整稳定哈希，verify_content=false 也不会跳过必要校验；报告明确 verify_content=true。轻量扫描属于 A4，尚未实现。

接口由 [main.py](../app/main.py) 提供：

1. GET /api/status 返回当前已授权根的 ID/别名，不给浏览器绝对目录或完整配置。
2. POST /api/scans 携带 Bearer、Idempotency-Key 和 root_id，立即返回 202 与 job_id，不让浏览器等待全部文件读完。
3. GET /api/jobs/{id} 查询真实任务阶段与报告。查询前重新验证当前根授权，不因曾经有任务就永久放行。
4. GET /api/scans/latest/{root_id} 只读最近报告，刷新/重新连接后可继续查看。

[jobs.py](../app/jobs.py) 的 ScanManager 只有一个后台扫描线程和一个应用变更锁，最多受理一个尚未结束的任务。新请求满额返回 429；重复请求先查幂等表，所以可以取回原 job_id。HTTP 主线程继续服务 /health 等请求。线程的 SQLite 连接按调用单独创建，不跨线程共享连接。将来执行器必须共享变更锁；本步没有开始文件执行功能。

进程锁负责“另一个程序别同时占用这份 DATA_DIR”；线程变更锁负责“本程序内部修改登记的工作按顺序来”。服务已持进程锁时，worker 只用应用变更锁；独立 CLI 自己持进程锁。正常退出会等待已受理扫描收尾后才释放锁。

[App.vue](../app/static/src/App.vue) 增加授权根选择、“扫描目录”“刷新扫描报告”、真实阶段、时间、计数、跳过原因和未成功项。每 500ms 查询正在执行的任务，结束后停止；不展示编造的百分比。所有文件名与错误路径通过 Vue 文本插值显示，不用 v-html。

token 仍只在页面内存，不进 URL/浏览器持久存储/日志。断开连接会取消页面请求、清除计时器和报告，但不会把已受理的后台扫描强行中断；重新连接可查报告。网络提交状态不明时，页面重试复用请求编号，减少重复受理。
